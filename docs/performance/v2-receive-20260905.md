## Delivered Behavior

The existing initial control lease now prepays one serialized packet/record
workspace using the local receive hard cap. Queued outbound data cannot consume
that workspace before an already admitted group's completion arrives. Other
groups and original destinations still reserve their own storage. The standing
floor can reject an outbound write earlier under the same total ceiling.

The real bidirectional regression admits 32 groups, queues a 1400-byte outbound
original that cannot yet seal, and successfully processes a finishing receive
shard with only 568 bytes of unreserved credit. Its delivery returns credit for
outbound progress. Asymmetric caps, larger bundles, prepaid constructor failure,
reentry and Close ownership are covered. Full product race/vet, 106 Python tests,
the nested probe race suite and independent integration review passed.

The optional `v2_receive` statistics distinguish cumulative handler/resource/
terminal events from current group/original/credit gauges. Counters survive
Session disposal; credit gauges cover the whole Peer, including outbound work
and handshake obligations. The reporter validates these fields when present,
supports older records without them, and reports counter deltas separately from
ending gauges. Sampling takes the existing owner mutex; it does not represent
an instantaneous, atomic snapshot of all socket/process counters. Runner/report
hashes changed for this optional instrumentation, while workload settings remain
the same. See [the API](../API.md) for precise counter semantics.

## Observed Saturation

The following receiver event deltas cover the aligned 15-second window. Gauges
are the ending snapshot, not deltas. Group completion means atomic fragment
admission into original reassembly, not necessarily business delivery. Bundles
and rejections count handler/admission attempts, including retries.

| V2 direction/profile | Bundles | New-group rejects | Original rejects | Completed / expired groups | End pending groups / originals | End credit bytes |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Upload | 177543 | 168004 | 0 | 1817 / 1057 | 1057 / 0 | 16762866 |
| Upload aggregation | 176801 | 168906 | 6 | 1494 / 866 | 884 / 427 | 16769104 |
| Download | 182913 | 0 | 0 | 36582 / 0 | 1 / 0 | 156591 |
| Download aggregation | 260082 | 0 | 0 | 52017 / 0 | 0 / 1 | 159205 |

Packet-workspace rejection is zero throughout. Both upload ending snapshots
have zero decoded groups waiting for original admission. Non-aggregated upload
samples 0 through 7 retain exactly 1057 incomplete groups. Each group reserves
14850 bytes, totaling 15696450 bytes; with other obligations, only 12302 bytes
remain under the 16777216-byte ceiling, less than one new group reservation.
Between samples 0 and 7, all 82496 handled bundles increment new-group rejection,
and group completion stays at 4635. Credit drops by 2048 bytes at sample 7 but
still cannot admit another group. Expiry begins at sample 8, about 11 seconds
after probe start including warmup, and briefly restores delivery before
saturation returns. The exact rows are in
`mpudp-p5-mpudp-upload-b1400-f1-diagoff-r1-v2/server-0.jsonl`:
sample 0 is line 4, sample 7 is line 11, and sample 8 is line 12.

This directly identifies byte admission blocked by incomplete state in that
interval. It does not prove why enough shards were lost initially, or make
increasing limits/shortening deadlines a performance fix. Aggregation additionally
retains incomplete originals. Dispatcher ingress drops and host load remain
part of the diagnosis; neither is equivalent to kernel UDP loss.

## Separate Profiles

The two profiled upload cases are separate from the six-case table. Receiver
`Controller.NextDeadline` still accounts for 12.10 seconds / 47.41% cumulative
CPU without aggregation and 11.80 seconds / 45.40% with aggregation. Flat shares
are 45.69% and 43.44%. These percentages overlap nested costs and must not be added.

The pending-group/original indexes removed their backlog scans, but path loops
remain. Profile lines 548 and 553 in this source copy reply/old-route records
while iterating the listener's 256 allocated path states; they contribute
10.10 seconds of flat CPU in the non-aggregated profile. The earlier local
microbenchmark used five path states and did not exercise this listener capacity.
The authenticated contract limits this client to five paths. A separate change
must verify runtime sizing against that contract and repeat the measurement.

CPU/mutex/block profiling begins after connection setup and spans warmup, steady
load, local drain and result exchange. Receiver CPU profile durations are
19.21 and 20.97 seconds. Allocation profiles also include earlier process startup;
heap in-use is a finalization snapshot. These are not steady-window allocation
rates or part of the unprofiled comparison.
